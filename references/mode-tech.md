# 技术文模式

适用:教程、实测、评测、工具/模型介绍、原理拆解、工作流分享。

## 一、结构模板

1. **现象开场**(25–35 字):一个具体现象或数字,不铺垫。
2. **为什么是现在**(2–4 段,每段 25–50 字):把这个现象和最近的变化挂钩,给出你的判断。
3. **给读者的承诺**(1–2 段):"跟着走一遍你也能做出 XX",降低门槛。
4. **准备清单**(可选,3–5 条列表):账号、工具、素材、成本。
5. **步骤正文**(3–8 步,每步:加粗小标题 + 60–120 字解释):
   - 小标题写动作,不写名词,例:`**1. 先买一个国产模型的 Coding 套餐。**`
   - 解释段讲"为什么这么做 + 具体怎么做 + 我踩过的坑",必要时给参数、命令、链接。
   - 每步后跟一张截图或一段 ≤25 字的短结论做节拍。
6. **成本与边界**(1–3 段):花了多少、耗时多久、什么情况下不适用。
7. **收尾**(25–40 字):一句判断或一句行动建议,不总结。

## 二、段落节奏

- 中位段长 30–35 字,长段(60–120 字)占比 12%–22%,单段不超过 150 字。
- **长段的唯一合法来源是步骤解释、原理拆解、踩坑复盘**;开场、过渡、结论一律短。
- 长段之后必须有短段(≤25 字)承接,例如一句"就这么简单。"或"这一步最容易翻车。"
- 段内最多 3 句;要讲三件事就拆三段。

## 三、证据与口径

- 每个结论都要能落地到"我做了什么、看到什么"。"我觉得好用"必须配具体场景。
- 数字口径统一:版本号写全、时间写"大约"、价格写原币种、性能写测试条件。
- 没有实测就明确写成"官方数据是…""我在文档里看到…",不许伪装成一手实测。
- 引用他人观点时给出来源与时间,并加上你的判断。

## 四、术语与读者友好度

- 术语第一次出现时用一句人话解释,例:"Agent(能自己调工具干活的 AI)"。
- 命令、参数、链接单独成段或放进代码块,不塞进长句。
- 面向小白的教程,每一步都要写"你应该看到什么",让读者能自查。

## 五、骨架示例(括号内为目标字数)

```
开场:现象 + 你的判断(30)
背景:这两天发生了什么(35)
背景:为什么值得学(45)
承诺:跟着做一遍能得到什么(30)
准备:需要的东西(列表 3–5 条)
步骤 1:加粗小标题
  解释:为什么 + 怎么做 + 坑(80–110)
  短句节拍(15)
  截图
步骤 2 …(同上)
成本:花了多少钱、多少时间(40)
边界:什么情况别用(35)
收尾:一句判断(30)
```

## 六、反例

- 通篇每段 80 字:语料里 80 字已是 p95,通篇这么写会累。
- 步骤写成"首先/其次/最后":应当用编号加粗小标题,让读者能跳读复现。
- 只讲结论不给过程:"我推荐这个工具"但没有实测、截图、成本,读者不会信。
- 结尾写"综上所述,XX 是大势所趋":改成一句具体判断,例"现在入场,成本不到一顿饭钱。"
